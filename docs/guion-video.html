Guion del Video

Sistema de Gestión de Cajas Automáticas — demostración del funcionamiento

Integrante: Vera, Enzo Duración objetivo: 10–14 min Escenas: 8

Objetivo (según la cátedra): "Video explicando el funcionamiento del sistema." No alcanza con mostrar pantallas — hay que explicar mientras se demuestra y dejar en evidencia que se cumplen los requisitos de la Aprobación.

Lo que el video debe demostrar

  • Login con JWT y 2 niveles de acceso
  • Protección de rutas por rol
  • CRUD simple completo
  • CRUD dependiente
  • Listado con filtro
  • Vista de detalle
  • Historia de usuario con valor de negocio
  • Validación y manejo de errores
  • Generación de PDF
  • Responsive / mobile-first
  • Backend en capas + ORM (Sequelize)
  • Tests como evidencia

Antes de grabar

  1. Datos limpios: corré el seed para tener datos coherentes — cd server && node seed.js
  2. Levantá los servidores: npm run dev desde la raíz (server + client), o usá el deploy.
  3. Credenciales a mano: Admin admin@taller.com / admin1234 · Técnico tecnico@taller.com / tecnico1234
  4. Cerrá pestañas y notificaciones. Navegador en pantalla completa.
  5. Tené a la vista la sección "Datos para cargar en vivo" (abajo) — ya están los datos del cliente, caja, reparación e ítems listos para copiar.
  6. Audio: lugar silencioso, hablá pausado. Si te trabás, repetí la escena (se corta en edición).

Escenas

01

Introducción

≈ 1 min
🎬 Mostrá

La pantalla de login con el logo.

🎙 Decí

"Hola, soy Enzo Vera. Este es el trabajo final de Desarrollo de Software: un sistema web para gestionar un taller de reparación de cajas automáticas de vehículos pesados, basado en un caso real de Rosario. El problema: un taller maneja muchos clientes, cada cliente tiene cajas, y cada caja pasa por varias reparaciones con un ciclo de vida definido. Hoy eso se lleva en papel; este sistema lo digitaliza. Está construido como una app full-stack con frontend y backend separados que se comunican por una API REST."

02

Login · Roles · Protección de rutas

≈ 2 min Imprescindible
  1. Entrá con password incorrecta → mostrá el error rojo "Credenciales inválidas".
    🎙 Decí

    "El backend valida las credenciales; si fallan devuelve un 401. Las contraseñas se guardan hasheadas con bcrypt, nunca en texto plano."

  2. Ingresá como Técnico. Señalá el menú: Dashboard, Cajas, Clientes, Perfil. No aparece "Usuarios".
  3. Escribí /usuarios en la URL → te redirige al inicio.
    🎙 Decí

    "Aunque escriba la URL a mano, la ruta está protegida: el sistema verifica el rol y me redirige. La protección está en el frontend y en el backend."

  4. Cerrá sesión y entrá como Admin → ahora SÍ aparece "Usuarios".
    🎙 Decí

    "Con rol de administrador tengo acceso a la gestión de usuarios. Estos son los dos niveles de acceso."

  5. (Opcional) En Usuarios, mostrá cambiar el rol de un técnico o atender una solicitud de reseteo.
03

CRUD Clientes · validación · filtro

≈ 2 min
  1. Andá a Clientes. Mostrá la lista.
  2. Buscá sin tildes (ej: "gonzalez") → filtra a "González".
    🎙 Decí

    "El listado tiene búsqueda con filtro, y algo a destacar: ignora tildes usando la extensión unaccent de PostgreSQL."

  3. Creá un cliente pero primero guardá sin nombre (o email inválido) → mostrá el error.
    🎙 Decí

    "La validación se hace en el backend con Zod. Si mando datos inválidos devuelve un 400 con el detalle. Nunca confío solo en el frontend."

  4. Completá bien (cliente Marcelo Funes — ver datos arriba) y guardá. Entrá al detalle del cliente.
  5. (Opcional) Intentá borrar un cliente con cajas → "No se puede eliminar".
    🎙 Decí

    "La baja valida dependencias: no me deja borrar un cliente que tiene cajas, para no romper la integridad."

04

Ciclo de vida de una reparación

≈ 4 min ★ La más importante

Es la historia de usuario con valor de negocio: cubre CRUD dependiente, PDF y flujo de estados. Dedicale tiempo.

  1. Cajas → mostrá el listado y los filtros (serie, tipo, cliente).
  2. Creá la caja ZF-6HP-2024-118 asociada a Marcelo Funes (ver datos arriba). Cada caja pertenece a un cliente — relación dependiente.
  3. Desde la caja, creá una Reparación con la falla declarada (ver datos arriba). Queda en estado "ingresada".
    🎙 Decí

    "La reparación depende de la caja, que depende del cliente: este es el CRUD dependiente."

  4. Mostrá el selector de estados.
    🎙 Decí

    "Cada reparación sigue un flujo con valor de negocio: ingresada → presupuestada → aprobada → terminada → entregada, o rechazada. Es el corazón del sistema."

  5. Pestaña Presupuesto: cargá los 4 ítems de la tabla de arriba (kit C2, solenoide, aceite, mano de obra). Los ítems dependen de la reparación.
  6. Descargá el PDF y abrilo en pantalla.
    🎙 Decí

    "El sistema genera el presupuesto en PDF al vuelo, con los datos del taller, el cliente, los ítems, el IVA y el total."

  7. Cambiá a "presupuestada" → "aprobada". Pestaña Trabajos: cargá los 3 trabajos de la tabla de arriba.
  8. Pestaña Fotos: subí una foto.
    🎙 Decí

    "Puedo adjuntar fotos; se suben a Cloudinary. En el celular se usa la cámara directamente."

  9. Cambiá a "terminada" → "entregada".
    🎙 Decí

    "Cierro el ciclo: la reparación queda entregada. Recorrimos toda la historia de usuario de punta a punta."

05

Dashboard

≈ 1 min
🎬 Mostrá

Las tarjetas con contadores por estado. Hacé clic en una para ir al listado filtrado.

🎙 Decí

"El dashboard da una vista general del taller: cuántas reparaciones hay en cada estado. Las tarjetas son clicables y llevan al listado filtrado por ese estado."

06

Responsive / PWA

≈ 1 min
🎬 Mostrá

DevTools (F12) → vista móvil. Navegá un par de pantallas: la navegación pasa a barra inferior y todo se adapta.

🎙 Decí

"La app está diseñada mobile-first y es totalmente responsive. En el celular la navegación se mueve a una barra inferior. Además es una PWA: se puede instalar como app desde el navegador."

07

Backend · arquitectura · tests

≈ 1–2 min
  1. Mostrá la estructura de server/: routes/, controllers/, models/, middlewares/, config/. Abrí models/index.js un segundo.
    🎙 Decí

    "El backend está en capas: las rutas reciben las peticiones, los controllers tienen la lógica, y los modelos de Sequelize —el ORM— mapean las tablas de PostgreSQL. Acá están las entidades y sus relaciones."

  2. Corré los tests: cd server && npm test Mostrá: 26 tests, 3 suites, todo en verde.
    🎙 Decí

    "Tests de integración con Jest y Supertest: 26 tests que cubren autenticación, roles, los CRUDs, la validación y el PDF. Todos pasan."

  3. (Opcional) Mencioná Vitest + Cypress en el frontend.
